# aiwf 使用手册

> 一句话：**你只在三个点说话——定 AC、审方案的理由、决定合并；中间由 agent 自己记录，gate 自动查，独立 agent 对账。**

---

## 0. 术语（先统一语言）

| 词 | 全称 / 含义 |
|---|---|
| **AC** | **Acceptance Criteria，验收条件**——这条需求"做完了"的可验证判定标准，二值（兑现/未兑现） |
| DoD | Definition of Done，团队通用完成标准（有测试、过 lint、文档更新），与具体需求无关 |
| story | 一个工作单元（对应一条 Jira story / issue） |
| **key** | tracker 号，如 `SHIP-1024`、`HKEI-52251`、禅道的 `2098`。**story 目录名用它**，操作时也用它 |
| gate | 程序化门禁：只查"字段填没填、AC 有没有人认领"，不读代码，零成本 |
| ac-check | 验收条件兑现检查：由**独立 session 的 agent** 判断每条 AC 是否真的被兑现 |
| review | 代码质量评审：规范、边界、可维护性。也必须独立 session |
| verdict | 判定：`pass` / `warn` / `block` |
| **认领** | 一条改动声明"我在兑现哪条 AC"。`record --criterion AC-x` 就是认领 |
| **转交（defer）** | 这条 AC 不归本 story（比如前端负责），有记录地移交，不再要求本 story 认领 |
| **过期认领** | AC 文本改过后，之前基于旧文本的认领自动失效，需要重新 `record` |
| **reopen** | 需求追加/变更时，把 story 退回某阶段；旧的 verify/review/ac-check 归档失效 |
| **commit 绑定** | verify / review 记录"验的是哪个提交"，代码再变则旧结论自动失效 |

**为什么要分三种检查**（不可互相替代）：

| 检查 | 抓得到 | 抓不到 |
|---|---|---|
| **gate**（规则） | 漏声明、越界、AC 没人认领、过期认领、代码变了旧结论没重做 | 挂了个编号但没真做 |
| **ac-check**（模型） | 挂编号但说明对不上、AC 未兑现 | 代码写错了（它不读代码） |
| **review**（模型） | 代码质量、边界、规范 | **漏做了一条需求**（没有的东西看不见） |

## 1. 安装与数据目录

```powershell
# 代码放哪
cd C:\Users\<你>\tools
git clone <仓库> aiwf

# 数据（stories）放仓库外，物理隔离，绝不可能被 push
setx AIWF_DATA "C:\Users\<你>\aiwf-data"
# 重开终端生效
python aiwf.py status
```

**工作数据目录一律放仓库外**（见 AIWF_DATA），仓库里只留代码和 md。

### ⚠ 环境变量的坑（最容易踩）

`AIWF_DATA` 是**环境变量，只在设了它的终端里生效**。所以很容易出现：

```
仓库内 ./stories    ← 旧终端（没读到变量）建的
外部 aiwf-data      ← 新终端建的
```

结果就是"story 散了、提示文件不一样"。三个命令解决：

```bash
python aiwf.py where     # 代码目录 + 当前数据目录 + 仓库内 ./stories，各列 story
python aiwf.py status    # 末尾显示当前数据目录；检测到分裂会警告
python aiwf.py adopt     # 把仓库内 ./stories 搬到当前数据目录（默认只预览，加 --yes 执行）
```

**`setx` 与 `$env:` 的区别**：

| 命令 | 生效范围 |
|---|---|
| `setx AIWF_DATA "路径"` | 之后**新开**的终端（永久） |
| `$env:AIWF_DATA = "路径"` | **当前**这个终端（临时） |

正确做法：先 `setx`，再**重开终端**，然后 `python aiwf.py where` 确认。

## 2. story 目录长什么样

```
2026-11-04-HKEI-52251-prospect/
  meta.json          # 状态、key、仓库列表、handoff 指针、已转交的 AC
  requirement.md     # 需求 + 澄清问答 + 编号化验收条件（AC-1、AC-2…）
  decisions.md       # 决策：结论 ← 被什么驱动 ← 何时可推翻
  plan.md            # 实施方案：改哪些文件、为什么
  changes.jsonl      # 每次改动一行；带 criteria + acHashes（认领时的 AC 版本）
  ac-check.jsonl     # 对账记录（可多次，取最后一次）
  verify.json        # 自检结果 + 验证的 commit
  review.json        # 独立评审结论 + 评审的 commit
  archive/           # reopen 时归档的旧 verify/review/ac-check（留档但失效）
```

**只有 `meta.json` 是必需的**，其余缺失时按空处理——所以旧 story 升级后能直接用。

## 3. 八个阶段（新增 ⑧ 需求追加）

### ① 接单

```bash
python aiwf.py init "fix-login-npe" --title "修复登录空指针" \
        --key SHIP-1024 --repo order-service
```

- `--key` 是 tracker 号（`--jira` 是它的别名）
- 目录名会变成 `2026-11-04-SHIP-1024-fix-login-npe`
- **不带 `--key`** 时退回当日序号 `2026-11-04-001-...`
- 同一个 key 只能有一个 story（重复会退出码 6）

### ② 澄清（人 + agent 聊，然后手改 requirement.md）

```markdown
## 澄清问答
- Q: NPE 在哪个入参？ A: 手机号为空
- Q: 期望行为？ A: 返回 400

## 验收条件
- [ ] AC-1 手机号为空时返回 400，不再抛 NPE
- [ ] AC-2 非空时行为不变（回归）
```

**写 AC 的要求：每条都能被测试或人工明确验证。** 写"优化体验"算不合格。

**编号规则**：写了 `AC-x` 就用你的编号；没写就按顺序自动编号成 `AC-1`、`AC-2`。
**建议显式写**——因为后面要引用它（`record --criterion AC-1`），而且改 AC 时编号保持不变才不会乱。

```bash
python aiwf.py gate <story>     # 确认澄清够了
```

### ③ 方案（agent 写 plan.md，**人只审「为什么」**）

```markdown
## 改哪些文件
| repo | 文件 | 改什么 | 为什么 |
|---|---|---|---|
| order-service | src/LoginService.java | 入参加判空 | 根因所在 |
```

> **人审的是理由，不是清单。** 理由对，范围大概率对；人查不出"漏了哪个文件"，也不该查。

```bash
python aiwf.py record <story> --stage planned --kind note --note "方案已定"
```

### ④ 实施（agent 改代码 + **自己跑 record 挂 AC**）

```bash
python aiwf.py record <story> --stage implementing --repo order-service \
        --file src/LoginService.java --criterion AC-1 --why "根因在入参未校验"

# 测试类改动挂另一条
python aiwf.py record <story> --repo order-service \
        --file src/LoginServiceTest.java --kind test --criterion AC-2 --why "补非空回归"
```

**在给 agent 的提示里写死这一条**：

> 每改完一处，必须执行 `python aiwf.py record ... --criterion <AC-x> --why "<为什么这处能兑现它>"`。说不清挂哪条，就说明这处改动可能不该做。

随时看余额：

```bash
python aiwf.py acs <story>
# ID        认领   转交  验收条件
# AC-1        1       手机号为空时返回 400
# AC-2        -       非空时行为不变（回归）
# AC-3        -    →  （已转交 frontend）
# 未认领：AC-2
```

**忘了挂？事后补**（不用删数据）：

```bash
python aiwf.py link <story> --target 2026-11-01T09:45:43 --criterion AC-1
```

**分工：有些 AC 不归你**（比如前端负责）：

```bash
python aiwf.py defer <story> AC-1 AC-2 --owner frontend --reason "前端仓库另有人负责"
```

转交的 AC 不再要求本 story 认领，`acs` 里标 `→`，对账提示词里会注明「不在本 story 范围」。
拿回来：`python aiwf.py undefer <story> AC-1`。

### ⑤ 对账（进 verifying 之前**必须**做一次）

```bash
python aiwf.py ac-check <story> > ac-prompt.md
# 把 ac-prompt.md 粘给一个【新开的】agent 会话
# 它返回：{"acs":[{"id":"AC-1","fulfilled":true}],"undeclared":[],"verdict":"pass"}

python aiwf.py ac-record <story> --verdict pass --fulfilled AC-1 --fulfilled AC-2
```

**这是唯一"必须"的人工介入点**，别省。

**触发提醒**：`record` 会在「自上次对账起满 3 条改动」时提示一次，不会每条都刷。

推荐时机：

| 时机 | 是否做 |
|---|---|
| 第一条改动之后 | ✅ 确认方向起对了 |
| 每个 repo 改完 | ✅ 建议 |
| **进 verifying 之前** | ✅ **必须**（gate 会拦） |
| 每条 record | ❌ 太贵 |

### ⑥ 自检

```bash
python aiwf.py verify <story> --cmd "mvn -q test" --result pass \
        --stage verifying --commit 3ef42576
```

**`--commit` 建议必填**：它是"我验的是这份代码"的证据。之后代码再变，gate 会拦：

```
x verify.json：验证的是 3ef42576，但当前提交是 b9890aee——代码变了，要重跑验证
```

### ⑦ 独立评审 + 交接

```bash
# 换一个 session 做代码评审
python aiwf.py review <story> --independent --reviewer reviewer-a --verdict pass \
        --issue "异常处理建议统一包装（下个迭代）" \
        --commit 3ef42576 --range 200c8d49..3ef42576

# 交接指针（给指针，不复制历史）
python aiwf.py handoff <story> --branch fix/npe --pr 128 --commit 3ef42576 --todo "等 CI"

python aiwf.py gate <story>      # 全绿 → 可以合并
```

**`--commit` 必须填**，而且要和 `handoff --commit` 一致——否则 gate 认为"评的是旧代码"：

```
x review.json：评审的是 3ef42576，但当前提交是 b9890aee——代码变了，要重新评
```

### ⑧ 需求追加 / 变更（不用重建 story）

**判断标准不是改动大小，而是"原来的 AC 还要不要重新保证"。**

```bash
python aiwf.py reopen <story> --reason "追加：prospect 类别"
```

它会：

1. 把 stage 退回 `clarifying`（可 `--stage planned|implementing` 指定）
2. **把 `verify.json` / `review.json` / `ac-check.jsonl` 移到 `archive/`**（留档但失效）
3. 记一条 reopen 流水

之后的路线和第一次一样，但**历史全部保留**：

```bash
# 1) 在 requirement.md 的「## 验收条件」追加新 AC
#    - [ ] AC-11 字段长度统一为 32
# 2) 认领（旧 AC 的认领仍然有效，不用重做）
python aiwf.py record <story> --file DDL.sql --kind config --criterion AC-11 --why "ALTER 列长"
# 3) 重新对账 → 验证 → 评审
python aiwf.py ac-check <story> > ac-prompt.md
python aiwf.py verify <story> --cmd "mvn test" --result pass --commit <sha>
python aiwf.py review <story> --independent --verdict pass --commit <sha>
```

| 情况 | 做法 |
|---|---|
| 同一需求的补充（加枚举值、补字段） | **同 story + `reopen`** |
| 影响面独立（DDL 跨端、要 DBA 评审、要单独排期） | **新建 story** |
| 纯 bug 修复（原 AC 没兑现） | 不 reopen，直接 `record` 修 + 重跑 verify |

## 4. 命令速查

| 命令 | 作用 |
|---|---|
| `init <slug> --title --key --repo` | 新建 story（`--jira` 是 `--key` 的别名） |
| `status [--all]` | 进行中的 story（含缺几条 AC）；`done` 默认隐藏 |
| `acs <story>` | 验收条件、认领数、转交情况、过期认领 |
| `context <story>` | 打包上下文（交接指针、AC 认领、最近改动、上次结论） |
| `record <story> --file --criterion --why [--kind] [--stage]` | 记一次改动，挂 AC |
| `link <story> --target <ts> --criterion` | 给已记录的改动补挂 AC |
| `defer <story> <AC...> --owner --reason` | 把 AC 转交出去，不再要求本 story 认领 |
| `undefer <story> <AC...>` | 把转交的 AC 拿回来 |
| `reopen <story> [--stage] --reason` | 需求追加：退回某阶段，旧结论归档失效 |
| `scan [路径] [--story]` | 扫描明文凭据（默认扫 story 目录，也可指定任意目录） |
| `scan <路径> --fix [--yes]` | 拆成脱敏模板 + `.local`（原值），并自动补 `.gitignore` 规则 |
| `where` | 代码目录 / 数据目录 / 仓库内 stories 各有几个 story |
| `adopt [--yes]` | 把仓库内 ./stories 搬到当前数据目录 |
| `handoff <story> --branch --pr --commit --todo` | 更新交接指针 |
| `ac-check <story>` | 生成兑现检查提示词（粘给新 session） |
| `ac-record <story> --verdict --fulfilled --issue` | 记录兑现检查结论 |
| `verify <story> --cmd --result [--commit]` | 记录编译/测试结果 |
| `review <story> --independent --verdict [--commit] [--range]` | 记录独立评审结论 |
| `gate <story>` | 检查门禁（失败退出码 2） |

---

## 5. 退出码

| 码 | 含义 | 怎么办 |
|---|---|---|
| 0 | 通过 | — |
| 1 | 找不到 story | 检查 slug / key |
| 2 | gate 失败 | 看输出里的 `x` 行 |
| 3 | review 没加 `--independent` | 确认换了 session 再加 |
| 4 | 挂了不存在的 AC | 用 `acs` 看可用编号 |
| 5 | link 的 target ts 不存在 | 从 `record` 输出里复制 |
| 6 | tracker 号已有 story / 目录已存在 | 打开原来那个 story，不要新建 |
| 7 | 这条 AC 已转交出去，不能在本 story 认领 | 先 `undefer` 再 `record` |
| 8 | `scan` 发现疑似明文凭据 | 移到环境变量或 `.local` 文件；提交过的先轮换 |

## 6. 日常节奏

| 什么时候 | 做什么 |
|---|---|
| 开新 story | `init --key` → 澄清 → 写编号 AC → `gate` |
| agent 改代码时 | 它自己 `record` 挂 AC |
| 每个 repo 改完 | `acs` 看一眼有没有 AC 没人认领 / 没挂 AC 的改动 |
| **进验证前** | `ac-check`（唯一必须的人工点） |
| 有人问"前端那条怎么办" | `defer` 转交，别忽略 |
| **需求追加** | `reopen` → 追加 AC → 重做对账/验证/评审 |
| 收工前 | `status` 看缺几条 AC、有没有过期认领 |
| 第二天开工 | `status`，再 `context` 恢复现场 |
| 换电脑 / 怀疑数据散了 | `where`，必要时 `adopt` |

## 7. 与 git / CI 集成

**pre-push hook**（`.git/hooks/pre-push`）：

```bash
#!/bin/sh
python aiwf.py gate "$AIWF_STORY" || exit 1
```

**CI 里**：`gate` 退出码非 0 就会让流水线红，所以可以当成"门禁第 0 关"。

## 8. 常见情况处理

| 情况 | 处理 |
|---|---|
| `gate` 说「AC 没人认领」 | 补做，或 `record` 说明为什么不需要改；不归你的用 `defer` |
| `gate` 说「改动没挂 AC」 | `link` 补挂；挂不上说明是越界改动，考虑撤掉 |
| `gate` 说「AC 文本改过，旧认领失效」 | 按新结论 `record --criterion AC-x` 一次即可 |
| `gate` 说「评审/验证的是 A，但当前提交是 B」 | 代码变了，重跑 `verify` / 重做 `review` |
| `gate` 说「最近一次验证结果是 fail」 | 修完重跑 `verify --result pass`；失败的记录不会因为后面又跑成功就自动算过 |
| `gate` 说「评审之后还有 N 条改动」 | 评审过期，重新 `review` |
| 担心仓库里有明文密码 | `python aiwf.py scan <目录>`，退出码 8 表示有命中 |
| 确认有明文密码要处理 | `python aiwf.py scan <目录> --fix` 预览 → `--fix --yes` 执行：原文件变脱敏模板，真实值移到 `.local`（自动加 gitignore） |
| `ac-check` 判 `block` | 补齐未兑现的 AC → 重新 `ac-check` → 改判 `pass` |
| `review` 判 `fail` | stage 自动打回 `implementing`，修完必须重评 |
| 需求追加 / 变更 | `reopen`，旧 verify/review/ac-check 自动归档失效 |
| 需求变了但只改 wording | 改 `requirement.md`；文本一变，旧认领自动失效（这是有意的） |
| 这条 AC 其实不归我 | `defer --owner --reason`，留记录；别直接删 |
| 做不下去 | `record --stage blocked`，`context` 里会带出来 |
| 换电脑后 story 不见了 | `where` 看数据目录；`AIWF_DATA` 只在设过它的终端生效 |

## 9. 设计原则

> 「我做了一个轻量的开发流程工具：把 story 的需求、决策、计划和变更做成结构化协议，
> 每条改动必须挂它兑现的验收条件，三个阶段各有一道检查——规则查字段、独立 agent 查兑现、独立 agent 查质量。
>
> 它不生成代码，生成交给模型；它解决模型做不了的三件事：**上下文供给、状态推进、结果验证**。
>
> 核心判断是：**AI 的可靠性不是靠模型变强解决的，是靠把「不可验证的部分」变成「可验证的」。**」
